# RTA Tool — project instructions

Dual-FFT audio measurement software. C++20. Licence **AGPL-3.0-or-later**.

## The one rule that governs the architecture

**`core/` must never include JUCE, Qt, or any audio-device API.**

`rta_core` takes `std::span<const float>` and returns numbers. Nothing else.
This is what allows every DSP claim to be proven on CI with no sound card and no
microphone — the property that separates this project from the analysers it
learns from.

The rule is enforced by the `core_has_no_framework_deps` ctest, which greps
`core/` for such includes and fails the pipeline. Do not weaken that test to make
a change compile. If core needs a platform capability, the *caller* in `app/`
supplies it as data.

## Verification standard

Do not write "done", "fixed", or "passing" without pasting the command and its
output. A green build proves the code compiles, not that the numbers are right.

DSP expectations must come from one of these, in order of preference:

1. **A closed-form identity.** Periodic cosine windows have exact analytic sums;
   assert those, not "whatever the code printed". See `core/tests/test_window.cpp`.
2. **A published standard.** IEC 61672-1 (weighting, detectors), IEC 61260
   (fractional-octave bands), IEC 60942 (calibrators). Cite the clause.
3. **A golden vector** generated by `tools/gen_golden.py` (NumPy/SciPy/pyrato)
   and committed under `core/tests/golden/`.

Never assert a value the implementation produced unless one of the three above
independently justifies it. That is a regression lock, not a correctness test —
label it as such if you add one.

## Real-time safety in `app/`

The audio callback copies into a lock-free ring buffer and does nothing else.
No allocation, no locks, no file I/O, no FFT. Analysis runs on its own thread and
publishes immutable snapshots by atomic pointer swap. Breaking this produces
dropouts at a live show, which is the exact situation this tool exists for.

## Module boundaries (added 2026-08-26 at the owner's instruction)

Four layers, each buildable and testable on its own. Dependencies point **down
only**; a lower layer never knows a higher one exists.

```
app/        rtatool      composition root: wiring + view models. No DSP, no drawing.
  |
ui/         az_ui        JUCE module: design system + reusable widgets.
  |                      PORTABLE -- knows nothing about audio measurement.
platform/   rta_platform audio device I/O behind an interface. JUCE on one side,
  |                      plain C++ types on the other.
core/       rta_core     pure DSP engine. No framework of any kind.
```

- `core/` and `ui/` are the two **portable** layers: either can be lifted into
  another project without dragging this one along. `ui/` is packaged as a JUCE
  module (`juce_add_module`), the same mechanism `melatonin_blur` uses, so
  adopting it elsewhere is one CMake line.
- `ui/` must contain **no measurement vocabulary**. Colours named `trace`,
  `coherence` or `target` are app semantics and belong in `app/`; `az_ui`
  supplies the palette, metrics, typography, primitives and LookAndFeel only.
  This is the line that decides whether the module is reusable or is just this
  app's GUI in a different folder.
- `platform/` exists so `core` never sees a device API and `app` never sees
  JUCE's audio classes directly.

## File length

**Hard cap 400 lines; aim for 300.** A file past that is doing more than one
job — split it along the seam that made it long. This applies to headers too.

## Which model does what

- **Opus** — design, architecture, planning, and short code written directly.
- **Sonnet or below (subagents)** — long or mechanical code: ports, bulk
  refactors, boilerplate. Dispatch with an exact spec and exact file paths.
- **Fable** — adversarial review. It reads the real files and tries to refute
  the claim that the work is done. Never review your own work.

## Reading out numbers

**Frequency displays as a whole number of hertz.** `1000 Hz`, not `1000.0 Hz`.
One-hertz resolution is already finer than any decision made while tuning a
system, and a decimal that never carries information costs a character on every
readout and invites a false sense of precision.

**dB keeps one decimal.** 0.1 dB is a real, actionable difference; 0.1 Hz is
not. Different quantities, different rules -- do not unify them for tidiness.

Coherence is 0..1 with two decimals.

## Seeing the GUI

Do not screen-capture the running app. Render it offscreen:

```
cmake --build build --config Release --target rtatool_snapshot --parallel
build/app/rtatool_snapshot_artefacts/Release/rtatool_snapshot.exe shots 1100 760
```

Then read `shots/specimen.png`. Screen capture of a live app fails for reasons
unrelated to the app -- another window drifts in front, desktop DPI scaling
rescales the result, layout has not settled after a resize, and the running
binary holds a lock on its own .exe so the next build cannot link. A snapshot
has none of those and is identical every run.

Invoke the exe through `cmd //c` from Git Bash; direct invocation returns 127.

Two things make a snapshot come out blank: `setSize()` does not call `resized()`
on a component with no desktop peer, and `createComponentSnapshot` needs `true`
for its children argument. Both are handled in `tools/snapshot.cpp`.

Credit: the technique is from the `juce-component-snapshot` skill in
PROJECT005-AZ-handsfree.
